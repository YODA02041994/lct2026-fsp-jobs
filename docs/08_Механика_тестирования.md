# Механика тестирования

Критерий № 2 (25 %). Проектирование 06.10.2026, до кода.

## 1. Что требует ТЗ и чего избегаем

| Отвергнутый вариант | Почему не годится | Наш ответ |
|---|---|---|
| Единый набор заданий | ответы разойдутся между кандидатами | каждому — уникальный экземпляр задания |
| Генерация заданий нейросетью под каждого | сложность несопоставима, оценка необъективна | уникальность достигается параметрами внутри шаблона с фиксированной сложностью, а не свободной генерацией |

## 2. Шаблоны заданий с параметрами

Единица банка — **шаблон**: компетенция, формат, уровень сложности, генератор экземпляров. Экземпляр создаётся
по случайному зерну: меняются данные, имена, числа, порядок вариантов, но проверяемое умение и сложность те же.

| Формат | Пример шаблона | Проверка |
|---|---|---|
| Предсказать вывод кода | фрагмент на Python или JavaScript со случайными значениями и именами | точный ответ |
| Запрос к данным | таблицы с случайными строками; вопрос «сколько строк вернёт запрос» или «какой запрос даст результат» | ответ или выбор |
| Найти ошибку | фрагмент с одной внесённой ошибкой из набора типовых | выбор строки |
| Оценить сложность или поведение | алгоритм с параметрами | выбор |
| Выбор решения | ситуация из практики (отладка, развёртывание, тестирование) с перемешанными вариантами | выбор одного или нескольких |
| Подход к решению | короткая задача от работодателя; свободный текст | оценивается работодателем или моделью, в грейд не входит |

Сложность шаблона задаётся грейдом при создании и уточняется по накопленным ответам (модель Раша: вероятность
верного ответа равна σ(θ − b), где θ — умение кандидата, b — сложность шаблона). Все экземпляры одного шаблона
делят одну сложность b — в этом сопоставимость между кандидатами.

Внешняя модель может предлагать **черновики новых шаблонов** по описаниям вакансий работодателей; в банк они попадают
после проверки человеком и калибровки, а не напрямую к кандидату. Так задания «от работодателя» появляются без потери
сопоставимости.

### Шкала сложности и грейда

| Грейд | Сложность шаблона b | Порог θ для грейда |
|---|---|---|
| Junior | −1,5 | θ ≥ −2,0 |
| Middle | −0,5 | θ ≥ −1,0 |
| Senior | +0,5 | θ ≥ 0,0 |
| Lead | +1,5 | θ ≥ +1,0 |

Пороги стоят посередине между сложностями соседних грейдов. Умение θ оценивается байесовской оценкой EAP с нормальным
априорным распределением N(0, 1) на сетке: она не разваливается при всех верных или всех неверных ответах и даёт
стандартное отклонение — меру уверенности. «Уверенно прошёл» = θ минус стандартное отклонение выше порога следующего грейда.

Для заданий, решающих грейд, предпочитаем форматы с точным ответом (вывод кода, число строк, значение): у них нет угадывания.
Там, где выбор неизбежен, — пять и более вариантов с перемешиванием; в модели ответа при валидации учитывается угадывание.

У каждого шаблона, кроме компетенции и сложности, есть **метки технологий**. Заявленный в опросе стек задаёт состав блоков:
каждый блок покрывает не меньше двух заявленных технологий. Технология считается **подтверждённой тестом** только если
по ней были задания и доля верных ответов не ниже порога; это поле `candidate_skill.confirmed_by_test` использует подбор.

## 3. Ход теста

1. Опрос: отрасль, специализация, стек, заявленный грейд.
2. Адаптивный сеанс: первый блок на уровне заявленного грейда; большинство верных — следующий блок на уровень выше,
   меньшинство — на уровень ниже. Размер блока и число блоков настраиваются (`TEST_BLOCK_SIZE`, `TEST_BLOCKS`);
   на стенде — два блока по пять заданий, чтобы тест занимал около десяти минут: жюри будет проходить его само.
   На задание отводится время, показывается ход теста.
3. Оценка θ (EAP) по ответам и сложностям шаблонов; грейд — по порогам θ; «уверенно» — см. шкалу выше.
4. Итог: грейд не ниже заявленного не понижается принудительно. Не прошёл — предлагается тест на уровень ниже;
   уверенно прошёл — предлагается тест на уровень выше. Смена грейда — не чаще раза в 90 дней (`grade_changed_at`).
5. Категория = специализация × подтверждённый грейд. Записывается история сеансов.

Защита от утечек: уникальные экземпляры, случайный порядок вариантов, время на задание, правильные ответы не показываются,
зерно экземпляра хранится для разбора спорных случаев.

## 4. Задания под вакансию

Из описания вакансии извлекаются технологии и компетенции → выбираются шаблоны, покрывающие их → собирается короткий
набор «под вакансию». Так показывается требование ТЗ: система формирует задания на основе описаний вакансий.
Те же наборы идут кандидатам как регулярные короткие задания от работодателя.

## 5. Процедура валидации (ТЗ называет метрики — считаем их)

Синтетические кандидаты с известным умением θ по грейдам; ответы моделируются по Рашу с поправкой на угадывание
в заданиях с выбором.

| Метрика ТЗ | Как считаем |
|---|---|
| Согласованность | один и тот же кандидат проходит тест дважды с разными экземплярами: доля совпавших грейдов, каппа Коэна |
| Дискриминативность | разделение соседних грейдов по θ (AUC); для каждого шаблона — корреляция ответа с итогом |
| Соответствие эталону | точность грейда против истинного, матрица ошибок |
| Устойчивость к утечке | кандидат «знает» ответы N чужих экземпляров: прирост оценки при параметризованных шаблонах против фиксированного набора |
| Корректность категоризации | доля верно определённых категорий |
| Пилот с людьми | участники команды проходят тест; результат сверяется с их реальным уровнем |

Скрипт: `scripts/validate_testing.py`, результаты — в `docs/09_Валидация.md`.

## 6. Что остаётся честно сказать

Банк в MVP небольшой. Свои шаблоны получают специализации **бэкенд, фронтенд, данные и машинное обучение, тестирование**;
остальные специализации проходят тест по общим компетенциям (SQL, алгоритмы, отладка, Git и процессы) — это написано
и в интерфейсе. Калибровка сложности по накопленным ответам показана на синтетических данных. Свободные ответы
«подход к решению» в грейд не входят. Для проверки пути работодателя без прохождения теста на стенде заведены
демонстрационные учётные записи кандидатов с готовыми результатами.

### Почему блоки, а не поэлементная адаптация

Проверили поэлементную адаптивную выдачу (CAT: каждое следующее задание — по текущей оценке θ) на той же симуляции
(`scripts/cat_experiment.py`, 400 кандидатов):

| Схема | Заданий | Точность грейда | Согласованность повтора |
|---|---|---|---|
| **блоки 2 × 5** | 10 | **0,65** | **0,57** |
| поэлементная | 10 | 0,56 | 0,54 |
| поэлементная, остановка по неопределённости | 8–12 | 0,58 | 0,54 |
| поэлементная | 15 | 0,59 | 0,52 |

При банке из четырёх уровней сложности поэлементная адаптация выигрыша не даёт: шаг между уровнями крупный, а первые оценки
θ по 1–2 ответам слишком шумные и уводят выдачу не туда. Остались на блоках; дальнейший рост точности — за счёт большего
числа заданий и калибровки сложности по накопленным ответам.
