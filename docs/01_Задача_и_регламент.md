## 4. Как оценивают

Экспертная комиссия ставит оценки от 1 до 5 по критериям из ТЗ и по пяти общим критериям (п. 5.25–5.26):

| Критерий | Что это значит для нас |
|---|---|
| Подход к решению (уникальность и оригинальность) | чем наша платформа отличается от обычного агрегатора: подтверждённый профиль достижений и подбор по нему |
| Техническая проработка | рабочий прототип, источники данных, поиск, устойчивость, документация |
| Соответствие задаче | покрытие всех пунктов ТЗ |
| Эффективность решения | измеримая польза: покрытие вакансий, качество подбора, скорость |
| Выступление на питче | только у финалистов, 24.10 |

Спецтрек проводится как соревнование по виду спорта «спортивное программирование», дисциплина «продуктовое программирование».
Правила вида спорта (приказ Минспорта России от 11.08.2023 № 584, п. 5.20.2; текст: `https://pravo.ppt.ru/pravila/286549`)
задают для этой дисциплины свои критерии, каждый от 1 до 10 баллов, оценивают три судьи-эксперта:

| Раунд | Критерии по правилам вида спорта |
|---|---|
| Квалификация | архитектура решения; структура данных; оценка кода; готовность решения — фронтенда и бэкенда |
| Защита | работоспособность прототипа; соответствие функциональным требованиям; технологичность; презентация; потенциал |

Защита по правилам длится 10 минут: 7 минут презентация и 3 минуты вопросы (п. 5.20.2.6).
Какая из двух систем критериев применяется на спецтреке, станет ясно из ТЗ. Готовимся к обеим:
код и структура данных должны выдерживать просмотр, прототип — работать целиком.

До 10 лучших команд проходят в финал (п. 5.12). Финалист подтверждает участие письмом лидера команды
в течение двух дней после объявления (п. 5.15).

Призовой фонд (п. 7.2): 1 000 000, 600 000 и 400 000 рублей до налога; приз делится между участниками команды поровну (п. 7.3).
Победители и призёры получают кубки, медали и дипломы Минспорта (п. 7.14).

## 5. Требования ТЗ (пересказ; файл ТЗ получен 06.10.2026, лежит в `docs/materials/`, в git не попадает)

### 5.1. Суть задачи

Веб-платформа подбора ИТ-специалистов с **обратной механикой**: не кандидат откликается на вакансию, а работодатель
просматривает базу кандидатов, разложенную по категориям, и сам направляет приглашение конкретному человеку с описанием
предложения и зарплатой. Эта механика названа смысловым центром конкурса и главным критерием оценки.
Ориентир — сервис LHH: инициатива у работодателя.

**Парсинг чужих сайтов и витрина чужих вакансий задачей не являются.** Платформа связывает напрямую только работодателя и соискателя.

### 5.2. Категория и грейд кандидата

| Элемент | Требование |
|---|---|
| Категория | связка «специализация × грейд» (например, бэкенд с опытом; фронтенд до года); справочник составляет команда, для MVP — основные направления |
| Как присваивается | обязательный путь при регистрации: опрос по отрасли и специализации → выбор предполагаемого грейда → тест на заявленный грейд; категория определяется результатом теста, а не самоописанием |
| Ранжирование внутри категории | выше те, у кого сильнее подтверждённый профиль: лучше результат теста, есть достижения в соревнованиях и мероприятиях ФСП |
| Смена грейда | по результату теста грейд принудительно не понижается: не прошёл — может пройти тест на уровень ниже; прошёл уверенно — повысить; смена ограничена по времени (пример — раз в три месяца, интервал выбирает команда) |
| Регулярные задания | система периодически предлагает кандидату короткую задачу от работодателя; результат влияет на актуальность профиля (желательно, не обязательно) |

### 5.3. Механика тестирования — отдельная проектная задача

Единый набор заданий не подходит: задания и ответы разойдутся между участниками рынка. Генерация уникальных заданий
нейросетью под каждого кандидата не гарантирует сопоставимую сложность и объективность. Нужен подход, устойчивый к обеим
проблемам; формат заданий — любой (код, опросники, иное). Достаточно нескольких описаний вакансий, на основе которых
система показывает, как формирует задания и тесты.

### 5.4. Связь с ФСП

Профиль кандидата должен уметь связываться с ID участника ФСП; в будущем ФСП ID будет работать на Keycloak, совместимость
упростит интеграцию, но способ авторизации выбирает команда. API, данные и структура данных ФСП намеренно не выдаются:
команда сама решает, какие сведения о достижениях получать и как показывать работодателю. Обязательна корректная обработка
кандидата **без истории ФСП**.

### 5.5. Данные и валидация

Готовых датасетов кандидатов, вакансий и эталонной разметки нет: команда работает на собственных данных — синтетических
или собранных из открытых источников. Команда **сама предлагает процедуру оценки своего решения, описывает её и приводит
результаты**; оценивается и решение, и качество системы его валидации.

### 5.6. Функциональность MVP

Два ролевых кабинета. Перечень задаёт минимум; реализацию и интерфейс выбирает команда.

| Кабинет кандидата | Обязательно |
|---|---|
| Профиль и резюме: вручную по форме или загрузка PDF с распознаванием (ФИО, контакты, стек, грейд, роли, стаж, гибкие навыки); автосборка стандартного PDF-профиля | да |
| Тестирование: опрос по отрасли и специализации, выбор грейда, тест; результат определяет категорию | да |
| Регулярные короткие задания от работодателей | желательно |
| Категория и грейд: текущий статус, история опроса и теста, тест на грейд ниже или выше с ограничением частоты | да |
| Входящие приглашения с вакансией и зарплатой; принять или отклонить | да |
| Список открытых вакансий, самостоятельный отклик, статусы откликов | желательно |
| Настройки: приватность (что видно работодателю), согласие на обработку и публикацию, связь с ФСП ID | да |
| Кандидат видит только свои приглашения и отклики | да |

| Кабинет работодателя | Обязательно |
|---|---|
| Профиль компании: описание, направление, контакты | да |
| Описание потребности: кто нужен, чем занимается команда, стек, специализация, грейд → подборка | да |
| Подборка: рекомендованные категории и кандидаты с обоснованием попадания | да |
| Поиск по банку кандидатов: фильтры по специализации, грейду, категории, стеку, наличию подтверждённых достижений ФСП | да |
| Приглашение кандидату с предложением и зарплатой, без привязки к вакансии; статусы приглашений | да |
| Публикация вакансий, входящие отклики | желательно |
| Контакты кандидата скрыты до принятия приглашения или его собственного отклика | да |

Поиск и подбор: выдача строится по категориям из опроса и теста, а не по самоописанию; ранжирование внутри категории по силе
подтверждённого профиля и по соответствию потребности работодателя с краткой объяснимостью; фильтрация и уточнение запроса
без потери ранее полученной подборки.

### 5.7. Правила данных

1. Зарплата обязательна и в вакансии, и в приглашении: диапазон «от–до» в рублях; кандидат видит условия до начала общения.
2. Приглашение содержит описание предложения, зарплату, название компании и способ связи; контакты кандидата открываются
   работодателю только после принятия приглашения или собственного отклика кандидата.
3. У приглашений и откликов есть статусы (например: отправлено, просмотрено, принято, отклонено); обе стороны видят статус.
4. Регистрация по электронной почте с подтверждением адреса. Проверка компании и модерация вакансий в MVP не требуются.
